## 一句话说清楚它干什么

选一份 PDF，什么都不用再点：有字的页直接读字和格线拼成表，扫描页有钥匙送 Gemini 认两遍对答案、没钥匙在浏览器里本地认（2026-11-01 施工单 010 加的，见文末「本地认字」），跨页的表接起来，Excel 自己下载。拿不准的格子标颜色，不悄悄填。

## 拍的板

Song 立的先后：**准 > 少动手 > 好看 > 快**。

**名字：扒表僧，副标题「施主丢卷，贫僧扒表」。** 照「X僧」的路子，「扒」是把表从 PDF 上扒下来，口语、带点土匪气，跟录入僧「施主去玩，贫僧填表」对仗。仓库名用拼音 `pabiao`。

**有字的 PDF 不用 AI。** pdf.js 读出每个字的坐标和格线，程序自己拼表。原因是「准」：字是从 PDF 里原样搬的，数字不经过任何模型，不会认错；也不花钥匙、不上传文件、不排队。AI 只在没字可读（扫描件）时上场。

**有格线的表按格线切，没格线的按字对齐。**
- 有格线（lattice）：从 pdf.js 的绘图指令里抠出横线竖线（描边的线、填色的细长方块都算），连成网格；两格之间缺线就是合并单元格。合并表头靠这个最准。
- 没格线（stream）：同一高度的字排成行，行里隔得远的字分成段；表身各行的段投影到横轴上，空隙就是列缝。表头里横跨几列的字（如「2024」盖着「实际 / 计划」）往两边撑，撑到最居中为止；落在两行表头中间的字（竖着合并的「产品」）当成竖向合并。
- 表头怎么认：从上往下，没有数字的行都是表头（只有年份的行也算表头，比如「2024　2025」）。

**跨页接表。** 上一页的最后一张表贴着页底（下面只有页脚）、下一页的第一张表贴着页顶（上面只有页眉）、列数一样，并且下一页的表没有表头或者表头一字不差，就接上；重印的表头只留第一份。

**数字照 PDF 的样子存成真数字。** 千分位、小数位数、括号负数 `(12)`、百分号、¥$ 前缀都变成 Excel 的数字格式，显示跟 PDF 一样，求和照样能求。日期认三种写法（`2025-03-14`、`2025/3/5`、`2025年3月14日`），存成真日期，显示照原样。
- `0` 开头的编号存成文字（格式设成 `@`）。一列里只要有 `0` 开头的编号、其余都是纯数字，整列都当编号存，免得同一列一半文字一半数字。
- 超过 15 位的数字串存成文字（Excel 存不准）。
- 像数字又不对劲的（`1,23`、`-0012`、`12.3.4`）照原样当文字，标黄。

**Excel 怎么排。** 一张表一个工作表（表1、表2…），表头加粗、灰底、合并单元格照原样，冻结表头。最后一张「扒表记录」：每张表在第几页、几行几列、表上方那行字（多半是表名）、要看的格子和原因、没扒成的页。没找到表时把正文按行放进「扒表记录」，不吐空表。

**扫描件：借 Gemini，认两遍对答案。** 录入僧踩过的坑：模型自己报的「拿不准」靠不住。所以每页认两遍（第二遍用拉过对比度的灰度图），逐格对；对不上认第三遍，过半的算数，没过半的标红并把几遍的结果写进批注。几遍认出来的表格形状都对不上，整张表标黄。
- 钥匙只存在用户浏览器的 localStorage，请求只走 `?key=`；报错原样显示 HTTP 状态码加谷歌原话；两把钥匙轮换，额度到顶自己等；模型名、`generationConfig` 的写法、429 的分法照抄录入僧网页版 `web/core.js`、`web/engine.js`。
- 没钥匙时不吐空表：停下来说「第 N 页是扫描件」，钥匙框就在下面，贴进去自动接着干，不用再点。有字的页照常先下载。

**界面。** 学苹果官网的长相：浅灰底 `#F5F5F7`、白色大圆角卡片、大号粗体标题、蓝色胶囊按钮 `#0071E3`、顶上半透明细条。交互照「人动手越少越好」：整块卡片都能点，也能直接把文件拖进页面；选完文件自动开干、干完自动下载。⚙ 里放两把钥匙、模型、制作人、「千手院总舵」「方丈邮箱」（mailto，点的时候顺手把邮箱复制好）。

**不卡死。** pdf.js 在 worker 里解析；每读一页让一下主线程；扫描页同时最多送 3 页。66 页 2970 行的样本 1.5 秒出表，主线程最长一次卡 358 毫秒。

**库从 CDN 引，版本钉死。** pdf.js 用 6.4.299 的 legacy 版（老一点的手机浏览器也能跑），配 `cMapUrl` + `cMapPacked: true`（不配中文会读成空白），再配 `standardFontDataUrl`、`wasmUrl`（扫描件常见的 JBIG2、JPX 图要用）、`iccUrl`。ExcelJS 4.4.0（SheetJS 社区版写不了颜色），带 SRI 校验。

## 本地认字（2026-11-01，施工单 010）

Song 原话："做个不要钥匙的，有人要求可能不高。中英文都要能识别。混着也没问题。"以前扫描页没钥匙就停下来要钥匙，现在没钥匙直接在浏览器里认，照样出表。

**用哪个 OCR：PP-OCRv5 mobile（PaddleOCR，ONNX，onnxruntime-web 跑）。** 跟 Tesseract.js 7（chi_sim+eng，best_int）比过：同一套收拾图、同一套拼表，只换认字那一步，10 份扫描样本逐格对答案。英文两家都行；中文 Tesseract 不行——中文 300 DPI 那份数字 51/57，其中 6 格悄悄错，150 DPI 和拍照的中文整张表塌了（0/57）；中英混排的文字格 16/48。PP-OCRv5 十份全部没有悄悄错的数字。代价是慢一倍（每页约 8–10 秒对 4–5 秒）、第一次多下载（约 25 MB 对约 7.5 MB）。照「准 > 少动手 > 好看 > 快」选 PP-OCRv5。数字见施工单 010 完工报告。

**模型放哪：本仓库 `models/`，跟网页同源。** 官方 PaddlePaddle 在 Hugging Face 上放的 ONNX（Apache-2.0），det 4.8 MB、rec 16.5 MB，都没过 50 MB。字典从 rec 的 `inference.yml` 抽出来存成 `ppocrv5_dict.txt`。第一次用时 Worker 下载，存进 Cache Storage（`pabiao-ocr-1`），以后不再下；onnxruntime 的 wasm 也走同一个缓存。来源、校验值写在 `models/README.md`。

**认字之前先把图收拾干净**（都在 Worker 里，不卡页面）：
1. 压平阴影：每 32 像素一块估纸的亮度（第 90 百分位），除掉。拍照的阴影、扫描的灰底一起去掉。
2. 扶正：试 −8° 到 8°，哪个角度横着投影最"齐"就是歪了多少，转回来。
3. 找表格线：横线竖线各扫一遍长黑段，允许线有点斜（透视），断成几截的同一条线接起来。两条防误认：线两边都得是白纸（糊在一起的字扫出来的"长黑段"上下都是墨）；不到 60 点长的线得碰着另一个方向的长线才算（字的笔画连起来也能有几十点长）。
4. 拍照的扳正：表的顶线和底线实际一样长，拿它们的四个端点算透视变换，把整张图拉回长方形，再找一遍线。只在有拍照证据时扳（竖线不平行，或者图的四边是桌面），扫描件不动。先试过找整张纸的四个角，阴影里的纸跟桌面一样暗，找不准，放弃了。
5. 擦掉表格线：不擦的话，紧挨竖线的数字会多认出一个 1 或 |。

**认字：** det（DB）在长边 1600 的图上找字块；字块跨过竖线就在竖线处切开（右对齐的数字常跟隔壁格左对齐的字连成一块）；再把四周放大过的框收紧到跟核心连着的墨上（不然会认出隔壁格的半个字）。rec 在原图上切，高 48 像素，CTC 解码，每个字带把握和大概的横坐标。然后按图上真实的空白分词、量出每段字真实的左右边和墨的高度（字号）。这样出来的"字块"跟有字 PDF 里 pdf.js 给的一样，直接交给原来那套拼表：有格线按格线切，没格线按字对齐，合并表头、跨页接表全都照旧。

**拿不准怎么标：**
- 黄：本地认的这格有字把握低（数字列低于 0.9，文字低于 0.6）；数字列里小数位数跟同列别的不一样；数字列里别的行都有数、这行别的格也有字，偏偏这格空着（多半漏认）。
- 橙：数字列里认成了字母、按数字改回来的。照录入僧的易混字：O/o/D/Q→0、I/l/|/i/!→1、Z/z→2、S/s→5、B→8、G/b→6、g/q→9；两头的杂点（竖线残渣认成的 ! | '）和落单的半边括号先去掉再试。改完能读成数字才改，读不成就照原样标黄。
- 红：几遍认得不一样（Gemini 那条路）。
- 本地认的页面上说一句："第 N 页是扫描件，贫僧本地认的，没上传。眼神差点，贴把钥匙更准。"钥匙框留着，贴进去就借谷歌重认，Excel 再下一次。

**有钥匙但出状况：自动改成本地认。** 钥匙无效、模型名不对、谷歌回坏 JSON、断网重试完、两把钥匙当天都用完——这些页都改成本地认，Excel 照样下载，谷歌原话照样显示在下面。每分钟次数到顶照旧等几秒再试（等得起）；当天额度用完以前是干等到太平洋时间半夜，现在不等了。

**本地认的页、没格线的表至少要 3 行分得开列。** 本地认会把标题里的「·」和全角空格两边分成两段，标题加副标题两行就能凑出一张"表"。有字 PDF 的门槛照旧是 2 行。

### 本地认字踩过的坑
- 线的回归斜率：一开始拿每段黑的中点当一个样本，一条直线上所有段的中点都一样，斜率算出来是乱数，线没擦掉还把格子切歪了。改成一段里每个像素都算一个点。
- 字号按 det 的框高算会偏大三成（框是放大过的），格子之间的缝看着就小，相邻两列被并成一列。改成量墨的高度。
- 糊的字的墨上下边不稳，同一行的字中心上下跳，一行表头被拆成两行。字的上下中心改用 det 框的，墨只用来量字号和左右边。
- 收紧框时不能切进 det 的核心：宋体里细细的 ll 墨太淡，按墨切会把 "mill" 切成 "mi"。
- 本机测试 `?ocr=tess` 能把认字换成 Tesseract.js（只在 localhost 认），留着给以后再比。
